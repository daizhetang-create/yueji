# 约己：产品与上线路线

更新：2026-08-18

## 结论

首发入口是 **微信小程序**，公开网页是今天就能使用和分享的过渡入口，原生 App 是自动读取冥想与运动数据的第二阶段。

这三个端不是三套产品：

```text
公开网页：立即访问、验证界面与日常流程
        ↓
微信小程序：微信登录、跨设备数据、微信支付、订阅提醒
        ↓
原生 App：Apple 健康 / Health Connect 自动判定完成
```

不选择纯网页做最终产品，因为打开路径和系统健康数据权限都不够好；不一开始做双端原生 App，因为微信支付、审核、备案和两套商店会拖慢首发；不选套壳式跨端小程序方案，因为支付与健康权限最终仍然要写原生能力，界面也更容易受模板限制。

## 产品已经砍到三页

### 今天

- 打开后直接看到今天的目标，没有仪表盘、社交动态和宣传文案。
- 默认给出“冥想 10 分钟”和“运动 20 分钟”，不要求用户先创建任务。
- 做完点一次整行即可；不需要上传截图或填文字。
- 新增目标只点一个预设，不走多步表单。

### 记录

- 只显示最近 7 天和今天每项是否完成。
- 不做伪洞察、复杂图表和游戏化等级。

### 我的

- 只放微信支付、完成判定和快速打开。
- 不预置朋友，不展示排行榜，不把失败金额做成炫耀指标。

## 为什么先用承诺金，而不是“失败后自动扣”

微信普通小程序支付可以按标准 JSAPI 链路接入，但预约扣费不是所有商户可直接开通的通用能力。官方文档在 2026-05 仍标记为灰度，且把预约扣费定义为“基于规则而非用户行为触发的单次扣款”，示例是票务和零售预约，不适合把“未完成健身目标”硬套进去。

首发资金模型因此是：

1. 用户建立 7 天约定，只确认一次微信支付，例如 `7 × ¥9.9 = ¥69.3`。
2. 每天完成，服务端记为可退还；失败则按事先同意的规则结算。
3. 周期结束，剩余承诺金调用微信退款原路退回。
4. 连续两次失败自动暂停下一周期，防止伤害性连扣。

这在行为上仍然利用了损失厌恶与承诺装置，但避免假装拥有并不匹配的免密代扣权限。资金归属、失败部分用途、退款时点和申诉规则必须在真实收款前完成法律与支付渠道审查。

## 今天已经完成

- 极简网页重构；
- PWA 安装能力和跨设备公开访问地址；
- 原生微信小程序代码；
- 微信登录、承诺金下单、支付回调验签解密、退款接口；
- GitHub 自动构建与发布；
- 加密单元测试与手机宽度浏览器验收。

## 今天仍需你提供的外部材料

这些不是代码能代办的资质：

1. 已认证的微信小程序 AppID 与 AppSecret；
2. 已开通小程序支付的微信支付商户号、API v3 Key、商户私钥/序列号、微信支付公钥/ID；
3. 企业主体和可用于接口回调的已备案 HTTPS 域名；
4. 最终的失败资金用途、退款规则、用户协议、隐私政策与客服联系方式。

拿到 1–3 后，当前工程无需改支付架构，只需填环境变量、部署服务端并在小程序后台配置合法域名。

## 上架节奏

### 第 1 周：小程序内部使用

- 认证小程序，完成备案和隐私配置；
- 部署服务端与数据库；
- 接入微信登录和普通小程序支付；
- 只开放 10–20 位熟人，逐笔人工复核退款；
- 验收零误扣、零重复订单、回调幂等、申诉可处理。

### 第 2–4 周：小程序提审

- 补齐用户协议、隐私政策、支付说明、订单/退款记录和账户删除；
- 加入订阅消息，但一天最多一条必要提醒；
- 用真实完成率、次日/七日留存和退款投诉决定是否扩大。

### 第 2 阶段：原生 App

- React Native 负责 iOS / Android UI 与共享业务逻辑；
- iOS 用原生 HealthKit 模块读取正念与训练记录；
- Android 用 Health Connect 读取 MindfulnessSessionRecord 和 ExerciseSessionRecord；
- 小程序继续作为微信支付、分享和低频入口。

选择 React Native 而不是把小程序直接套壳成 App，是为了保留更好的界面控制，同时能接原生健康权限；支付、约定、结算等领域模型可与现有 TypeScript/Node 服务共享。

## 发布闸门

只有以下项目同时满足才向非熟人开放真实资金：

- 支付回调验签、幂等、查询补偿和日对账全部通过；
- 退款与申诉有明确 SLA，人工可介入；
- 完成证据有宽限期，时区/断网/数据延迟不会误判；
- 失败资金用途经法律与渠道审查，并在付款前显著告知；
- 健康数据最小化采集，可撤回授权、导出和删除账户。
